# 경계 검사: 한 번 지불하거나 생략하기

커널 안의 `a[i]`에는 안전 검사가 숨어 있습니다. 컴파일러는 이를 “`i`가 슬라이스 안에 있는가? 아니면 커널을 중단하라”로 바꾸며, 모든 스레드의 모든 접근마다 비교와 분기를 실행합니다. CPU에서는 거의 눈에 띄지 않지만 GPU 핫 루프에서는 차이가 큽니다. `gemm` 예제의 순진한 GEMM은 곱셈-누산마다 두 번의 검사에 대부분의 시간을 쓰며 RTX 5090에서 약 2,940 GFLOPS를 냅니다. 검사를 제거한 같은 커널은 7,160 GFLOPS를 기록합니다.

이 장에서는 안전성을 포기하지 않고 성능 차이를 줄이는 방법을 다룹니다. [안전성 모델](the-safety-model)을 바탕으로 합니다. `DisjointSlice`가 병렬 쓰기의 데이터 경합을 막고, 검사된 `PreparedLaunch`가 호스트에서 실행 형상을 증명한다는 점을 알고 있다고 가정합니다. 같은 아이디어, 즉 적절한 위치에서 사실을 한 번 확인하고 타입에 증명을 담는 방식을 읽기와 버퍼 크기에도 적용할 수 있습니다.

안전한 순서부터 가장 직접적인 방법까지 세 가지 도구가 있습니다.

| 도구 | 기능 | 안전성 |
|:--|:--|:--|
| 읽기 뷰 | 행이나 열 전체가 유효한지 한 번 검사한 뒤 추가 검사 없이 읽습니다. | 완전히 안전 |
| 실행 계약의 `requires` | 실행마다 버퍼 크기를 CPU에서 한 번 검사합니다. | 완전히 안전 |
| `#[kernel(unchecked_indexing)]` | 인덱스 검사를 제거하고 올바른 인덱스 사용을 호출자에게 맡깁니다. | 틀리면 UB |

## 경계 검사 비용

A의 한 행과 B의 한 열 사이 내적은 간단해 보입니다.

```rust
let mut sum = 0.0f32;
let mut i = 0;
while i < k {
    sum += a[row * k + i] * b[i * n + col];
    i += 1;
}
```

각 반복에서 실행되는 내용을 세어 보면 다음과 같습니다.

```text
i < k              루프 종료 검사 (필요)
row*k + i < a.len  경계 검사, 트랩 분기 (추가 비용)
load a
i*n + col < b.len  경계 검사, 트랩 분기 (추가 비용)
load b
fma
```

세 비교 중 두 개는 추가 비용입니다. 또한 루프 본문을 여러 기본 블록으로 나눠 언롤링을 막습니다. 컴파일러가 이를 자동으로 없앨 수는 없습니다. 컴파일러는 `a.len()`을 불투명한 값으로 보며 `row * k + i`가 그보다 작다고 알 방법이 없습니다. 호스트에서 버퍼 크기를 정한 **여러분**은 그 사실을 알고 있지만, 그 정보가 다른 프로그램에 있는 셈입니다. 이 장의 나머지 내용은 그 사실을 컴파일러에 전달하는 방법을 설명합니다.

## 읽기 뷰: 한 구간을 한 번 검사하기

행렬은 GPU 메모리에 행 단위로 이어진 긴 배열로 저장됩니다. API에서 `stride`라고 부르는 **행 너비**는 한 행의 원소 수입니다. `(row, col)` 원소의 평탄화 인덱스는 `row * stride + col`입니다.

```text
3 x 4 행렬, stride = 4:

  col:      0   1   2   3
  row 0:  [ 0   1   2   3 ]     row(1)은 평탄 인덱스 4, 5, 6, 7을 가리킴
  row 1:  [ 4   5   6   7 ]     col(2)는 평탄 인덱스 2, 6, 10을 가리킴
  row 2:  [ 8   9  10  11 ]              (단계마다 4씩 이동)
```

`MatrixView32`는 일반 `&[f32]` 매개변수와 행 너비를 함께 감쌉니다. 행이나 열을 요청할 때 “구간 전체가 슬라이스 안에 있는가?”를 **한 번** 검사하고, 이후 추가 경계 검사 없이 읽을 수 있는 뷰를 반환합니다.

```rust
let a_mat = MatrixView32::new(a, k);   // A는 각 행 너비가 k인 m개 행
let b_mat = MatrixView32::new(b, n);   // B는 각 행 너비가 n인 k개 행

if let Some(a_row) = a_mat.row(row, k)      // A의 행 전체를 한 번 검사
    && let Some(b_col) = b_mat.col(col, k)  // B의 열 전체를 한 번 검사
{
    // a_row / b_col을 통한 모든 읽기는 추가 검사 없이 수행
}
```

검사에 실패하면 `None`을 반환하고 포인터는 만들어지지 않습니다. `unsafe`도 필요하지 않습니다. 읽기는 데이터 경합을 만들지 않으므로 여러 스레드가 겹치는 읽기 뷰를 가져도 됩니다.

### 내적 검사 결합: `zip_exact`

뷰 하나를 순회할 때 반복자의 “다음 원소가 있는가?” 검사는 루프 종료 조건이므로 원시 포인터 루프에도 필요합니다. 그러나 내적은 뷰 두 개를 순회합니다. 두 반복자를 일반적인 `zip`으로 묶으면 매 단계 양쪽을 검사합니다. `zip_exact`는 행과 열의 길이가 같은지 **한 번** 확인한 뒤 하나의 카운터로 두 뷰를 순회합니다.

```rust
if let Some(pair) = a_row.zip_exact(b_col) {
    let mut sum = 0.0f32;
    for (x, y) in pair {
        sum += x * y;
    }
}
```

결과 루프는 다음 형태입니다.

```text
a 읽기, b 읽기, fma, 증가, 비교, 분기
```

이는 직접 작성한 원시 포인터 루프와 정확히 같은 형태입니다. [`gemm_views`](https://github.com/NVIDIA/cuda-rust/tree/main/cuda-oxide/crates/rustc-codegen-cuda/examples/gemm_views) 예제는 이를 입증합니다. 안전한 커널과 `unsafe` 원시 포인터 버전을 함께 컴파일하고, PTX의 분기 수와 메모리 명령이 같고 루프 안에 트랩이 없으며 GPU 결과가 비트 단위로 같은지 확인합니다. 1024×1024×1024 크기의 측정 결과입니다.

| 커널 | GFLOPS | 설명 |
|:--|--:|:--|
| `gemm` (일반 `a[i]`) | 2,942 | 곱셈-누산마다 검사 두 번 |
| 순진한 뷰 (안전) | 7,159 | 2.4배, 검사를 한 번만 수행 |
| 순진한 원시 포인터 (`unsafe`) | 7,161 | 안전성 비용 약 0.1% |

### 뷰와 배리어

커널에서 `sync_threads()`를 사용할 때는 모든 스레드가 배리어에 도달해야 합니다. 뷰 검사에 실패한 스레드도 조기에 반환하면 안 됩니다. 대신 빈 뷰를 사용하고 읽기는 기본값으로 처리합니다.

```rust
let a_row = a_mat.row(row, k).unwrap_or(RowView32::empty());
// ... 이후 타일 로딩 루프에서:
tile[idx] = a_row.get(i).unwrap_or(0.0);   // 비교 한 번, 경계에서는 0
```

`get`은 비교 하나의 비용이 듭니다. 핫 루프가 아닌 경계 처리를 위한 접근자입니다. `gemm_views`의 타일 커널도 이 패턴을 사용합니다.

## 결과 쓰기: 행 너비가 런타임 값인 타일

쓰기에는 [안전성 모델](the-safety-model)에서 설명한 `DisjointSlice`를 계속 사용하는 것이 안전합니다. 새로 소개할 `tile_2d32_rt`는 크기를 컴파일 시점에 알 수 없는 출력 행렬을 위해 `n` 같은 런타임 행 너비를 사용하는 2D 타일입니다.

```rust
// `c` 자체에 행 너비가 들어 있으며 호스트에서 같은 `n`으로 설정합니다.
// 따라서 스레드별 너비를 호출에 전달할 필요 없이 안전합니다.
if let Some(mut cell) = c.tile_2d32_rt(coord) {
    let previous = cell.at_const::<0, 0>().read();
    cell.at_const::<0, 0>().write(alpha * sum + beta * previous);
}
```

왜 너비를 인자로 전달하지 않고 슬라이스에 저장할까요? 타일 간 비중첩성, 즉 “서로 다른 스레드 좌표는 겹치지 않는 사각형을 소유한다”는 주장은 모든 스레드가 같은 행 너비를 안다는 전제를 암묵적으로 둡니다. 두 스레드가 너비를 다르게 알면 같은 메모리를 서로 다른 격자로 해석할 수 있습니다. 1×1 타일에서 너비 5인 스레드 `(1, 0)`은 평탄 인덱스 `1*5 + 0 = 5`를 얻고, 너비 100인 스레드 `(0, 5)`도 `0*100 + 5 = 5`를 얻습니다. 같은 원소에 두 개의 `&mut`가 생겨 데이터 경합이 발생합니다.

이전 설계는 너비를 `unsafe` 호출 인자로 받았지만, 호출 지점의 의무만으로는 이 문제를 막지 못했습니다. 안전 코드에서도 스레드마다 달라지는 조건으로 두 “균일한” 너비 중 하나를 고를 수 있기 때문입니다. 그래서 행 너비를 슬라이스에 저장합니다. 호스트가 실행 전에 `cuda_host::RowWidth`를 통해 한 번 지정하고, 디바이스 코드는 이를 바꿀 수 없으므로 `c`에 접근하는 모든 스레드는 같은 너비를 사용합니다. 너비가 컴파일 시점에 알려져 있다면 `tile_2d32`를 사용하세요. 너비가 다르면 타입 오류가 발생합니다.

## `requires`: 실행 시 크기 조건 지정

뷰는 다른 보장이 없으므로 런타임에 `a.len()`과 비교해 구간을 확인합니다. 하지만 호스트는 버퍼를 할당했기 때문에 크기를 알고 있습니다. 실행 계약의 `requires` 키에 그 사실을 커널 선언과 함께 적을 수 있습니다.

```rust
#[kernel(launch_context = lc)]
#[launch_bounds(256)]
#[launch_contract(domain = 2, coordinates = u32, block = (16, 16, 1),
    requires = (k >= 1, a.len() >= m * k, b.len() >= k * n, c.len() >= m * n))]
pub fn sgemm_naive_views(m: u32, n: u32, k: u32, alpha: f32,
    a: &[f32], b: &[f32], beta: f32,
    mut c: DisjointSlice<f32, RuntimeRowMajorTiles<1, 1>>) {
```

생성된 실행 메서드는 GPU 작업을 시작하기 전에 CPU에서 실행마다 각 관계를 한 번씩 확인합니다. 관계를 만족하지 않는 실행은 커널 중간에 오류를 내는 대신 조건을 설명하는 오류를 반환합니다.

```text
sgemm_naive_views: 크기 조건 `a.len() >= m * k` 위반:
좌변은 8192, 우변은 16384입니다.
```

관계식은 임의의 Rust 코드가 아니라 의도적으로 제한된 문법을 사용합니다. 슬라이스 매개변수의 `name.len()`, 부호 없는 정수 스칼라 매개변수, 정수 리터럴, 괄호, `+ - *`를 사용해 비교식 하나를 만듭니다. 이유는 두 가지입니다.

1. 모든 식별자를 실제 커널 매개변수와 대조하므로 오타는 잘못된 값 검사로 조용히 넘어가지 않고 컴파일 오류가 됩니다.
2. 모든 `+`, `-`, `*` 연산은 검사된 `u64` 연산으로 컴파일되므로 큰 `m * k`가 오버플로해 작은 값으로 바뀌어 잘못 통과하지 않습니다.

`_unchecked` 실행 메서드는 실행 형상 검사와 마찬가지로 이 검사도 건너뜁니다. 따라서 조건을 지키는 책임이 `SAFETY` 계약에 포함됩니다.

## 탈출구: `unchecked_indexing`

뷰로 접근 패턴을 표현할 수 없고 커널의 정확성을 확인했다면 직접적인 방법을 사용할 수 있습니다.

```rust
#[kernel(unchecked_indexing)]
pub fn hot_loop(a: &[f32], b: &[f32], mut c: DisjointSlice<f32>) {
    let idx = thread::index_1d().get();
    if let Some(out) = c.get_mut(thread::index_1d()) {
        *out = a[idx] + b[idx];   // 검사와 트랩 없음
    }
}
```

이 설정은 커널 안의 모든 `a[i]` 인덱싱 검사를 제거합니다. `get_unchecked`와 같은 계약으로 모든 인덱스가 유효하다고 약속해야 합니다. 그렇지 않으면 트랩이 발생하지 않고 관련 없는 메모리가 조용히 손상될 수도 있는 정의되지 않은 동작(UB)이 됩니다. `unsafe` 키워드를 쓰지는 않지만 그에 준해 취급하세요.

실험용으로 전체 빌드에 적용하는 옵션도 있습니다.

```console
$ CUDA_OXIDE_UNCHECKED_INDEXING=1 cargo oxide build my_example
$ cargo oxide build my_example --unchecked-indexing   # 같은 설정
```

적용 범위를 정확히 알아 두세요.

- 배열 인덱싱(`a[i]`) 검사만 제거됩니다. 산술 오버플로, 0으로 나누기 등 다른 안전 검사는 계속 트랩을 일으킵니다. 범위 인덱싱(`&a[i..j]`)도 계속 트랩을 일으킵니다.
- 커널별 설정은 인라인된 함수를 포함해 해당 커널 본문에 적용됩니다. 다른 커널로 전파되지 않습니다. 이 커널의 도우미 함수를 호출하는 별도 커널은 자신의 검사를 유지합니다.
- 검사된 빌드가 통과한 뒤, 가능하면 `compute-sanitizer`로 검증한 경우에만 사용하세요. [`unchecked_indexing`](https://github.com/NVIDIA/cuda-rust/tree/main/cuda-oxide/crates/rustc-codegen-cuda/examples/unchecked_indexing) 예제에서 설정 전후의 PTX를 확인할 수 있습니다.

## 도구 선택

```text
뷰로 접근 패턴(행, 열, 타일, 내적)을 표현할 수 있는가?
├── 예 → 뷰와 `requires` 계약을 사용합니다. 안전하며 원시 포인터만큼 빠릅니다.
└── 아니요 → 커널의 정확성을 검증했는가(새니타이저, 테스트)?
    ├── 예 → #[kernel(unchecked_indexing)]을 사용하고 unsafe 코드처럼 문서화합니다.
    └── 아니요 → 검사를 유지합니다. 7,000 GFLOPS의 잘못된 결과보다
                  트랩이 있는 2,900 GFLOPS가 낫습니다.
```

## 요약

- `a[i]`는 접근마다 비교와 분기 비용이 듭니다. 핫 루프에서는 주된 비용이며 순진한 GEMM에서 2.4배 차이를 만듭니다.
- 읽기 뷰(`MatrixView32::row` / `col`, `zip_exact`)는 구간 전체를 한 번 확인해 내부 읽기의 검사를 제거합니다. 완전히 안전하며 PTX가 직접 작성한 `unsafe` 코드와 같습니다.
- `requires = (...)`는 버퍼 크기 검사를 호스트로 옮깁니다. 커널 도중 트랩하는 대신 실행마다 타입이 지정된 오류를 반환합니다.
- `#[kernel(unchecked_indexing)]`은 인덱스 검사를 제거합니다. `get_unchecked`와 같은 계약이며 범위를 벗어나면 정의되지 않은 동작입니다.
