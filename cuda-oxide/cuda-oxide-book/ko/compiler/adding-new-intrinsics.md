# 새 내장 함수 추가하기

cuda-oxide는 두 가지 고유 기여 경로를 가지고 있습니다. 대부분의 장치 내장 함수는 ** 카탈로그 생성 **: 기여자는 검토 된 카탈로그 입력을 편집하고 `cuda-intrinsics-gen`API, 방언, 수입자, 하위 변환, 목표, 참조 및 탐사 표면을 함께 생산합니다. 카탈로그가 표현할 수없는 맞춤 검증 또는 하위 변환 작업은 손으로 남아 있습니다.

[카탈로그 생성 내장 함수]](catalog-generated-intrinsics.md)로 시작하십시오. 기존 카탈로그 모델이 작업을 표현할 수 없다는 것을 확립하지 않는 한. 이 장은 컴파일러 단계와 손으로 작성된 경로를 문서화하여 생성 내적 요소를 해당 단계를 통해 흐르는 표현의 구체적인 예로 사용합니다.

---

## 5단계 파이프 라인

모든 GPU 내장 함수는 컴파일러를 통해 동일한 경로를 따라갑니다:

```text
cuda-device          User writes:  thread::threadIdx_x()
    │
    ▼
mir-importer       Compiler sees the call, emits a `dialect-nvvm` op
    │
    ▼
dialect-nvvm       The op lives here as a verified IR node
    │
    ▼
mir-lower          Converts the `dialect-nvvm` op into an LLVM dialect op
    │
    ▼
llvm-export        Exports textual LLVM IR  →  llc turns it into PTX
```

에`mir-lower`두 가지 전략 중 하나를 선택합니다.

|전략            | 사용 시                                                                  | 예제|
| :------------------ | :--------------------------------------------------------------------------- | :------------------------------------- |
|LLVM 내장 함수 호출 | LLVM은 이미 그 기능을 가지고 있습니다                                           | `threadIdx_x`경전 , 장벽|
|직선 PTX 조립체 | LLVM 내장 함수는 존재하지 않거나 PTX 명령에 대한 정확한 통제가 필요합니다 | `trap`, `wgmma`, `tcgen05`, `mbarrier`|

두 전략은 아래에서 보여집니다.

## 예제 1: `threadIdx_x` (단순 사례)

`threadIdx_x()`GPU 내장 함수의 "Hello, World"입니다: 0개의 논증, 1개의 `u32`이 예제를 따라가면, 간단한 내성 값을 추가할 수 있습니다.

### 단계 1 - `cuda-device`로 선언

**파일:** `cuda-oxide/crates/cuda-device/src/thread.rs`

```rust
#[inline(never)]
pub fn threadIdx_x() -> u32 {
    unreachable!("threadIdx_x called outside CUDA kernel context")
}
```

두 가지 규칙은 트릭을 이해하기 전까지는 이상하게 보일 수도 있습니다.

- **`#[inline(never)]`**는 MIR에서 함수를 별도의 호출으로 표시합니다.
rustc가 이 코드를 내장하면 컴파일러는 `unreachable!()` 대신 수신할 수 있는 호출을 볼 수 있습니다. 그건 도움이 되지 않을 것입니다.

- **이 함수는 실제로 실행되지 않기 때문에 몸은 `unreachable!()`**입니다.
컴파일러는 모든 GPU 코드가 실행되기 전에 전체 호출을 `dialect-nvvm` 동작으로 대체합니다. 함수를 플래스홀더로 생각하십시오. "사랑하는 컴파이러, 여기에 GPU 명령어를 삽입하십시오".

```{tip}
LLVM IR 또는 PTX가 함수의 위의 댓글에서 본질적인 지도를 문서화하십시오. 미래 (또는 미래의 기여자) 는 현재 당신에게 감사 할 것입니다.
```

### 단계 2 - 을 정의합니다.`dialect-nvvm`오프

**파일:** 에 있는 손으로 쓴 op 모듈 중 하나`cuda-oxide/crates/dialect-nvvm/src/ops/`- `asm.rs`, `atomic.rs`, `cluster.rs`, `debug.rs`, `grid.rs`, `memory.rs`또는`wgmma.rs`.

```{important}
두 종류의 작전이 진행되고 있습니다`dialect-nvvm`, 그리고 그 중 하나만 손으로 쓴다.

에 의해 묘사 된 모든 것`intrinsics/catalog.json`에 의해 ** 생성됩니다**`cuda-intrinsics-gen`로`cuda-oxide/crates/dialect-nvvm/src/ops/generated/`모든 파일은 으로 시작됩니다.`// @generated by cuda-intrinsics-gen ... DO NOT EDIT.`아래의 예로 사용된 작전은 그 중 하나입니다: `tid.x`카탈로그가 본질적이고 그 작업은`ops/generated/sreg.rs`오늘, 수동으로 작전을 추가하면 다음 발전기 실행에 의해 취소됩니다.

생성된 파일의 소유자인 기여자 작업 흐름, 덮개, 첨부만 하는 ABI 레저, 재생, 증거 및 로컬 CI 게이트를 포함하여 [카탈로그 생성 내재] ](catalog-generated-intrinsics.md)를 참조하십시오.

위와 같은 모듈은 손으로 작성된 모듈입니다. 카탈로그에서 설명하지 않은 맞춤형 확인 또는 낮추는 ops입니다. 이 섹션의 코드는 op가 양쪽 방향으로 어떤 형태를 취하는지 보여줍니다. 두 번째 유형에만 직접 작성하십시오.
```

```rust
#[pliron_op(name = "nvvm.read_ptx_sreg_tid_x", dialect = "nvvm", format)]
pub struct ReadPtxSregTidXOp;

impl Verify for ReadPtxSregTidXOp {
    fn verify(&self, ctx: &Context) -> Result<(), Error> {
        let op = &*self.get_operation().deref(ctx);
        if op.get_num_operands() != 0 {
            return verify_err!(op.loc(), "expected 0 operands");
        }
        if op.get_num_results() != 1 {
            return verify_err!(op.loc(), "expected 1 result");
        }
        Ok(())
    }
}
```

그럼 등록해줘요. 그럼 더 많은 사람들이 이 작전이 존재한다는 걸 알 수 있을 겁니다.

```rust
pub(super) fn register(ctx: &mut Context) {
    ReadPtxSregTidXOp::register(ctx, ReadPtxSregTidXOp::parser_fn);
}
```

`Verify`트리트 (trait) 는 구조적 버그를 일찍 발견합니다. 만약 뭔가 실수로 두 개의 오페란드를 가진 이 작업을 만들면, 세 단계 후에 쓰레기 PTX를 생성하는 대신 명확한 메시지로 검증이 실패합니다.

### 단계 3 -- `mir-importer`에서 인식

**파일:** `cuda-oxide/crates/mir-importer/src/translator/terminator/intrinsics/generated/` 아래의 내장 함수의 가족 모듈

번역기가 MIR를 처리할 때 모든 함수 호출이 을 통과합니다.`try_dispatch_intrinsic()``terminator/mod.rs`. 호출자의 완전 자격 도메인 이름 (FQDN) 은`CrateDef::name()`을 통해`extract_func_info()`,  같은 경로를 생성`cuda_device::thread::threadIdx_x` 같은 카탈로그를 위해`tid.x`, `try_dispatch_intrinsic()`생성된 디스파셔에 지연, 그 일치 팔은 FQDN을 검사합니다:

```rust
"cuda_intrinsics::__cuda_oxide_intrinsic_abi_v1::i0001"
| "cuda_device::thread::threadIdx_x"
| "cuda_device::threadIdx_x" => {
    require_arity(name, args.len(), 0, &loc)?;
    Ok(Some(helpers::emit_generated_nvvm_intrinsic(
        ctx,
        body,
        ReadPtxSregTidXOp::get_concrete_op_info(),
        "v1:i0001",
        destination, target, block_ptr, prev_op,
        value_map, block_map, loc,
    )?))
}
```

팔은 전체 모듈 경로 (`cuda_device::thread::threadIdx_x`) 와 재출출된 이름 (`cuda_device::threadIdx_x`) 과 버전 ABI 위명 (alias) 을 일치시킵니다. 따라서 사용자가 함수를 수입하는 방식에 관계없이 호출이 가로막습니다. FQDN은 일치하기 위해 사용됩니다. 본질적인 검사 전에 `::`에서 `__` 변환이 일어나지 않습니다.

`emit_generated_nvvm_intrinsic()`helper는 *어떤* 제로항쟁, 단일 결과 NVVM 내장 함수에 대해 작동합니다. NVVM 연산을 삽입하기 전에 MIR 목적지를 준비하고, 카탈로그 ABI 마커로 연산을 태그하고, 준비된 목적지를 통해 결과를 작성하고, 다음 기본 블록에 브랜치를 발산합니다. 이 팔을 직접 작성하지 않습니다. 검토 된 덮개, ABI, 그리고 증거 입력으로 해결되면`intrinsics/catalog.json`, `cuda-intrinsics-gen`발산합니다.`terminator/mod.rs`카탈로그가 설명할 수 없는 것만을 위한 존재입니다.

### 단계 4 - LLVM 방언으로 내려가기

**파일:** `cuda-oxide/crates/mir-lower/src/convert/generated_intrinsics/` 아래의 내장 함수의 가족 모듈

이 작전은`MirToLlvmConversion`op 인터페이스. 카탈로그 내장 함수 impl은 공유 변환기와 함께 생성됩니다:

```rust
#[op_interface_impl]
impl MirToLlvmConversion for ReadPtxSregTidXOp {
    fn convert(
        &self,
        ctx: &mut Context,
        rewriter: &mut DialectConversionRewriter,
        _operands_info: &OperandsInfo,
    ) -> Result<()> {
        convert_zero_operand_scalar_direct(
            ctx,
            rewriter,
            self.get_operation(),
            32,
            "llvm_nvvm_read_ptx_sreg_tid_x",
        )
    }
}
```

공유 변환기는 LLVM 내장 함수 호출을 발산합니다:

```rust
fn convert_zero_operand_scalar_direct(
    ctx: &mut Context,
    rewriter: &mut DialectConversionRewriter,
    op: Ptr<Operation>,
    width: u32,
    intrinsic_name: &str,
) -> Result<()> {
    let result_ty = IntegerType::get(ctx, width, Signedness::Signless);
    let function_ty = llvm_types::FuncType::get(ctx, result_ty.into(), vec![], false);
    let call = call_intrinsic(ctx, rewriter, op, intrinsic_name, function_ty, vec![])?;
    rewriter.replace_operation(ctx, op, call);
    Ok(())
}
```

카탈로그가 아닌 작업에 대한 수필 변환은 `convert/interface_impls.rs`에서 동일한 패턴을 따르며, `convert/intrinsics/` 모듈에 위임됩니다.

```{note}
LLVM 내재 이름은 점 (`llvm.nvvm.read.ptx.sreg.tid.x`) 을 사용하지만 플리론 식별자는 점을 포함할 수 없습니다. 내부적으로 우리는 하부자 (`llvm_nvvm_read_ptx_sreg_tid_x`). 수출 단계에서는 다시 변환합니다.
```

**파일:** `cuda-oxide/crates/llvm-export/src/export/` (수출 모듈)

`CallOp`수출자는 이미 하부점으로 변환을 처리합니다:

```rust
let fixed_name = if name.starts_with("llvm_nvvm") {
    name.replace('_', ".")
} else {
    strip_device_prefix(&name)

```

`threadIdx_x`가 *not* 컨버전트 (이건 스레드별 레지스터 읽기, 집단 연산이 아닌)이기 때문에, `is_convergent_intrinsic()`에 추가할 것이 없다.

```llvm

```

`llc` 다음:

```text
mov.u32  %r1, %tid.x;
```

## 예제 2: `shuffle_xor` (복합 사례)

워프 셔플은 더 흥미롭다. 사용자의 단축 문법은 두 개의 논리를 통과하지만 기본 LLVM 내장 함수는 * 4 * 를 기대한다. 한 가지 추가 (원자 마스크) 는 소스 수준에서 채워지고 다른 하나는 (클램프) 는 하위 변환 것으로 채워진다. 이 작업은 또한 ** 컨버전스 ** 이다. 즉 LLVM은 제어 흐름에 이동, 중복 또는 추측해서는 안 된다.

### 단계 1 - `cuda-device`로 선언

**파일:** `cuda-oxide/crates/cuda-device/src/warp.rs`

```rust
#[inline(never)]
pub fn shuffle_xor_sync(mask: u32, var: u32, lane_mask: u32) -> u32 {
    let _ = (mask, var, lane_mask);
    unreachable!("shuffle_xor_sync called outside CUDA kernel context")
}

#[inline(always)]
pub fn shuffle_xor(var: u32, lane_mask: u32) -> u32 {
    shuffle_xor_sync(u32::MAX, var, lane_mask)
}
```

내장 함수인 은 마스크 입니다`_sync`형태, 이전과 같은 패턴;`let _ = (mask, var, lane_mask);`사용되지 않는 변수 경고를 제거합니다. 아무 대가 없이 작은 예의를 합니다.`shuffle_xor`단축은 단절이 아닙니다.`#[inline(always)]`  마스크를 공급하는 포장을`u32::MAX`을 불러서 만 불러`_sync`이름은 컴파일러에 의해 항상 일치합니다. 래퍼는 평범한  코드입니다.

### 단계 2 - 을 정의합니다.`dialect-nvvm`오프

**파일:** `cuda-oxide/crates/dialect-nvvm/src/ops/generated/warp_shuffle.rs`. 워크 셔플은 `tid.x`와 같은 카탈로그 내장 함수이기 때문에 이 op는 타이핑하기보다는 생성됩니다. 실제 정의는 다음과 같습니다.

```rust
/// Exchange a 32-bit value with a named XOR partner lane.
///
/// Operands are `[member_mask, value, lane_or_delta]`.
/// Generated lowering inserts the fixed clamp required by the selected shuffle mode.
#[pliron_op(
    name = "nvvm.shfl_sync_bfly_i32",
    format,
    interfaces = [NOpdsInterface<3>, NResultsInterface<1>],
)]
pub struct ShflSyncBflyI32Op;

impl Verify for ShflSyncBflyI32Op {
    fn verify(&self, ctx: &Context) -> Result<(), Error> {
        let op = self.get_operation().deref(ctx);
        if op.get_num_operands() != 3 || op.get_num_results() != 1 {
            return verify_err!(
                op.loc(),
                "nvvm.shfl_sync_bfly_i32 requires exactly [member_mask, value, lane_or_delta] and one result"
            );
        }
        // ... i32 type checks on all three operands and the result ...
        Ok(())
    }
}
```

이번에는 세 개의 연산자 (원자 마스크, 값, 경로 마스크) 를 사용해서 하나의 결과를 얻습니다.

### 단계 3 -- `mir-importer`에서 인식

**파일:** `cuda-oxide/crates/mir-importer/src/translator/terminator/intrinsics/generated/` 아래의 내장 함수의 가족 모듈

```{important}
워프 셔플은 카탈로그 내재성입니다. 그래서 그들의 전송 팔과`generated/warp_shuffle.rs`2단계 작전과 함께, 에 대한 모든 것이 손으로 기록되어 있습니다.`try_dispatch_intrinsic()``terminator/mod.rs`그리고 카탈로그가 설명할 수 없는 것을 포함합니다. 예를 들어,`core::intrinsics::typed_swap_nonoverlapping`(원시적인 뒤에 `core::mem::swap`) 는 여기에 맞게 되어 있고, 손으로 쓰인 글씨로 낮춰져 있습니다.`emit_typed_swap()`같은 파일에서 두 개의 중복되지 않는 포인터에서 로드/로드/스토어/스토어를 교차합니다.
```

논증으로 내장 함수된 것은 op를 구축하기 전에 사용자의 각 연산자를 번역합니다. 여기에는 `shuffle_xor_sync`에 대한 생성된 팔이 있습니다.

```rust
"cuda_device::warp::shuffle_xor_sync" => {
    require_arity(name, args.len(), 3, &loc)?;
    let (member_mask, last_op) =
        rvalue::translate_operand(ctx, body, &args[0], /* ... */)?;
    let (value, last_op) =
        rvalue::translate_operand(ctx, body, &args[1], /* ... */)?;
    let (lane_or_delta, last_op) =
        rvalue::translate_operand(ctx, body, &args[2], /* ... */)?;
    let shuffle = ShflSyncBflyI32Op::build(ctx, member_mask, value, lane_or_delta);
    shuffle.deref_mut(ctx).set_loc(loc.clone());
    helpers::set_generated_intrinsic_marker(ctx, shuffle, "v1:i0051");
    let (prepared_destination, prepared_last_op) = helpers::prepare_destination_write(
        ctx, body, destination, value_map, block_ptr, last_op, loc.clone(),
    )?;
    helpers::insert_op(ctx, shuffle, block_ptr, prepared_last_op);
    let result = shuffle.deref(ctx).get_result(0);
    Ok(Some(helpers::emit_prepared_result_and_goto(
        ctx, prepared_destination, result, target, block_ptr, shuffle,
        value_map, block_map, loc,
        "shuffle_xor_sync call without target block",
    )?))
}
```

팔은 사용자의 MIR 연산자를 플리론 값으로 번역합니다. 일반적으로 각 연산자의 할로카 슬롯에서 `mir.load`의 결과 또는 문자적 인 인분자에 대한 `mir.constant`의 결과를 번역합니다, 그 다음 NVVM 연산을 삽입하기 전에 호출 목적지를 준비합니다. 그 결과 그 준비된 목적지를 통해 나중에 기록되므로, 본질적인 실행이 끝난 후 동적 투사는 재평가되지 않습니다. (이것들은 아직 SSA 값이 아닙니다. 번역이 완료되면 `pliron::opts::mem2reg`는 로드/스토어 체인을 붕괴시킬 것입니다.) 카탈로그 내장 함수에 대해서는 이것의 어떤 것도 쓰지 않습니다: `cuda-intrinsics-gen`은 그것을 해결된 생성 카탈로그에서 파생합니다.

### 단계 4 - LLVM 방언으로 내려가기

**파일:** `cuda-oxide/crates/mir-lower/src/convert/intrinsics/warp.rs`

여기서 네 번째 주장이 나타납니다.`dialect-nvvm`op는 세 개의 연산자를 가지고 있으며, 나비 셔플의 LLVM 내장 함수는 ** 네 개 **를 가지고 있습니다:

```text
User's shorthand: shuffle_xor(value, lane_mask)                     →  2 args
Intrinsic stub:   shuffle_xor_sync(mask, value, lane_mask)          →  3 args
                                   ^^^^
                                   u32::MAX from the Stage 1 wrapper
LLVM intrinsic:   shfl.sync.bfly.i32(mask, value, lane_mask, clamp) →  4 args
                                                             ^^^^^
                                                             always 31
```

변환기는 세 개의 연산자를 전진하고 클램프 상수를 추가합니다:

```rust
pub(crate) fn convert_shuffle_i32(
    ctx: &mut Context,
    rewriter: &mut DialectConversionRewriter,
    op: Ptr<Operation>,
    _operands_info: &OperandsInfo,
    intrinsic_name: &str,
    clamp: i32,
) -> Result<()> {
    let i32_ty = IntegerType::get(ctx, 32, Signedness::Signless);

    let operands: Vec<_> = op.deref(ctx).operands().collect();
    if operands.len() != 3 {
        return pliron::input_err_noloc!(
            "Warp shuffle i32 requires 3 operands [mask, value, lane_or_delta]"
        );
    }
    let (mask, val, lane_or_delta) = (operands[0], operands[1], operands[2]);

    let clamp_val = create_i32_const(ctx, rewriter, clamp);

    let func_ty = llvm_types::FuncType::get(
        ctx,
        i32_ty.into(),
        vec![i32_ty.into(), i32_ty.into(), i32_ty.into(), i32_ty.into()],
        false,
    );

    let call_op = call_intrinsic(
        ctx, rewriter, op, intrinsic_name, func_ty,
        vec![mask, val, lane_or_delta, clamp_val],
    )?;
    rewriter.replace_operation(ctx, op, call_op);
    Ok(())
}
```

마스크는 여기 있는 평범한 연산자이고 변환기가 만든 상수가 아닙니다.`u32::MAX`(모든 32번 차선 참가)`_sync`사용자를 어떤 마스크를 통과 할 수 있습니다.`31`, 생성된 에 의해 셔플 모드에 의해 공급`MirToLlvmConversion`이 변환기를 호출하는 impl는 셔플이 전 경전 폭을 다는 것을 의미합니다. 그것은 명령 모드의 고정된 특성이고, 사용자에게 노실행키는 것은 그저 소음일 것입니다.

### 단계 5 -- 수출 (동결성 추가)

워프 셔플은 ** 컨버전트 ** - LLVM은 제어 흐름에 비해 재질서해서는 안됩니다. 수출 단계에서는 `is_convergent_intrinsic()`를 확인합니다:

```rust
fn is_convergent_intrinsic(name: &str) -> bool {
    name == "llvm.nvvm.barrier0"
        || name.starts_with("llvm.nvvm.shfl")      // shuffles
        || name.starts_with("llvm.nvvm.vote")       // votes
        || name.starts_with("llvm.nvvm.mbarrier")   // async barriers
        || name.starts_with("llvm.nvvm.cp.async.bulk")
        // ...
}
```

만약 당신의 새로운 내장 함수인 것이 컨버전스라면, 여기에 추가하십시오. 당신이 잊어버리면, LLVM은 그것을 `if` 블록에서 꺼내서, 당신의 워크 레벨 코드가 잘못된 결과 또는 교착점을 생성할 수 있습니다. 훌륭하지 않습니다.

** 최종 생산량:**

```llvm
declare i32 @llvm.nvvm.shfl.sync.bfly.i32(i32, i32, i32, i32)

%v8 = call i32 @llvm.nvvm.shfl.sync.bfly.i32(
    i32 -1, i32 %v3, i32 %v4, i32 31) #0

attributes #0 = { convergent }
```

`llc` 다음:

```text
shfl.sync.bfly.b32  %r3, %r1, %r2, 31;
```

## 인라인 PTX 경로

일부 작업에는 LLVM 내장 함수가 없습니다. 그 경우 직렬 PTX 조립을 직접 발산합니다. 보조자 `inline_asm_convergent()`는 보일러 플레이트를 처리합니다:

```rust
// wgmma fence: no inputs, no outputs, just a side effect
inline_asm_convergent(
    ctx, void_ty.into(), vec![],
    "wgmma.fence.sync.aligned;", ""
);

// mbarrier arrive: one input (pointer), one output (token)
inline_asm_convergent(
    ctx, i64_ty.into(), vec![ptr_val],
    "mbarrier.arrive.shared.b64 $0, [$1];", "=l,r"
);
```

제약 문자열은 LLVM 인라인 어셈블리 문법을 따릅니다:

|제한 | 의미|
| :--------- | :-------------------------------------- |
|`=l`       | 출력: 64비트 레지스터|
|`=r`       | 출력: 32비트 레지스터|
|`r`        | 입력: 32비트 레지스터|
|`l`        | 입력: 64비트 레지스터|
|(무료)    | 입력 또는 출력 없음 (상작용만)|

`sideeffect convergent`인라인 어셈블리에 있는 마커들은 LLVM에게 그냥 두라고 말합니다. 움직이지 말고, 삭제하지 말고, 복제하지 마세요.

## 끝에서 끝까지: 전체 여행

여기 모든 표현이 있습니다`threadIdx_x`위에서 아래로 지나가며:

```text
Rust:         thread::threadIdx_x()
MIR:          _3 = threadIdx_x() -> bb1
Pliron MIR:   %v = nvvm.read_ptx_sreg_tid_x : i32
Pliron LLVM:  %v = call i32 @llvm_nvvm_read_ptx_sreg_tid_x()
LLVM IR:      %v5 = call i32 @llvm.nvvm.read.ptx.sreg.tid.x()
PTX:          mov.u32 %r1, %tid.x;
```

그리고`shuffle_xor_sync` 뒤에 있는 `shuffle_xor`단축:

```text
Rust:         warp::shuffle_xor_sync(u32::MAX, val, lane)
MIR:          _5 = shuffle_xor_sync(const u32::MAX, _3, _4) -> bb2
Pliron MIR:   %v = nvvm.shfl_sync_bfly_i32 %mask, %val, %lane : u32
Pliron LLVM:  %v = call i32 @llvm_nvvm_shfl_sync_bfly_i32(i32 -1, %val, %lane, i32 31)
LLVM IR:      %v8 = call i32 @llvm.nvvm.shfl.sync.bfly.i32(i32 -1, %v3, %v4, i32 31) #0
PTX:          shfl.sync.bfly.b32 %r3, %r1, %r2, 31;
```

6개의 표현식. 하나의 Rust 함수 호출이 하나의 PTX 명령이 된다. 중간 단계가 존재하기 때문에 각 변환은 작고 검증 가능하며 독립적으로 테스트될 수 있다.

## 빠른 참조 체크리스트

손으로 작성된 본질적인 (한 `intrinsics/catalog.json` 설명 할 수 없습니다), 당신이 만질 필요가 있는 모든 파일, 순서:

1. **`cuda-device/src/<module>.rs`** -- `pub fn`와 `#[inline(never)]` 그리고
`unreachable!()`이것은 사용자-대면 API입니다.

2. **`dialect-nvvm/src/ops/<module>.rs`** -- `#[pliron_op(name = "nvvm.<name>", ...)]` 구조,
`Verify`imp (운동자/결과 수를 확인)`register()`전화해

3. **`mir-importer/src/translator/terminator/mod.rs`** -- `match` 팔을 들어
`try_dispatch_intrinsic()`, 손으로 쓴 것 처럼`typed_swap`0-운동수와 내적은 카탈로그 영역입니다. 생성된 디스파이터는`helpers::emit_generated_nvvm_intrinsic()`, MIR 몸체를 스레드하여 생성된 작업 전에 목적지가 준비되고 또한 손으로 작성된 팔이 직접 스탬프해야 할 ABI 마커를 스탬핑합니다.

4. **`mir-lower/src/convert/interface_impls.rs`** -- `MirToLlvmConversion`
새로운 오프에 대한 임플, 변환기 기능에 전송.

5. **`mir-lower/src/convert/intrinsics/<module>.rs`** -- 변환 로직.
LLVM 내장 함수에 대해 `call_intrinsic()` 또는 inline PTX에 대해`inline_asm_convergent()`를 사용하십시오.

6. **`llvm-export/src/export/`** -- *만 konvergent *: 에 더하기
`is_convergent_intrinsic()`.

카탈로그 내장 함수, 단계 2에서 4까지 당신은 작성 할 수 없습니다. 적절한 확장 `intrinsics/overlay/*.toml`가족, ABI 항목을 에 첨부합니다.`intrinsics/abi-v1.toml`, 경로가 필요할 때만 증거를 추가하고 재생합니다. `intrinsics/catalog.json`생성되어 손으로 편집해서는 안 됩니다.[카탈로그 생성 내성적](catalog-generated-intrinsics.md)전체 작업 흐름에 대한 것입니다.
